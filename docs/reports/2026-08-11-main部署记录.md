## 3. 服务器登录与代码同步

通过 SSH 登录：

```bash
ssh root@8.136.8.223
cd /www/wwwroot/FCN_SweetSeek
```

服务器原先位于 `jackie` 分支，并存在未提交修改和未跟踪文件。为避免覆盖服务器现场，先完整暂存：

```bash
git stash push -u -m "server-backup-before-main-deploy"
git fetch origin
git checkout main 2>/dev/null || git checkout -b main origin/main
git pull --ff-only origin main
```

需要恢复部署前的服务器修改时，可使用：

```bash
git stash list
git stash show --stat stash@{0}
git stash pop stash@{0}
```

恢复前应先确认当前分支，避免把 `jackie` 分支的修改误应用到 `main`。

## 5. 后端依赖与 Gunicorn 重启

```bash
cd /www/wwwroot/FCN_SweetSeek

if [ ! -d venv ]; then
  python3 -m venv venv
fi

source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
pip install gunicorn gevent
```

本次服务器没有对应的 Gunicorn systemd 服务，后端通过独立 Gunicorn 进程运行。停止旧主进程后启动新实例：

```bash
kill <OLD_GUNICORN_MASTER_PID>
sleep 3

nohup venv/bin/gunicorn -c gunicorn_config.py app:app \
  > /www/wwwlogs/sweetseek_backend.log 2>&1 &
```

验证新实例正常后，清理残留旧进程。不要在未确认新实例可用前强制终止全部 Gunicorn 进程。

## 7. 本次问题与注意事项

1. 本地 Windows 的 `bash.exe` 是未安装 WSL 时的占位入口，无法直接执行 Linux `deploy.sh`，因此本次通过 SSH 在服务器逐步部署。
2. 部署前服务器处于 `jackie` 分支且有未提交修改，不能直接重置或覆盖；使用带 `-u` 的 Git stash 完成可恢复备份。
3. 直接访问公网 IP 返回 Nginx 默认站点的 `404`，属于虚拟主机未匹配；使用 `sweetseek.top` 域名访问正常。
4. Gunicorn 旧工作进程曾短暂处于 `D` 状态，启动新实例并验证后再清理，避免服务中断。
5. 密码和私钥不得写入仓库、部署脚本或本记录。
